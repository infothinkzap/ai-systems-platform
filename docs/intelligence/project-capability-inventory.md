## Implementation plan and acceptance

Extend the existing graph types, loader, queries and relationship dictionary. Keep Product IDs/statuses intact. Add a Project with direct implementation evidence, evidence-qualified Capability metadata, proposed Opportunity/Workflow/WorkflowStep entities, allocations, risks, validation requirements and delivery-readiness records. Reuse existing Problem/Persona/Data/Capability IDs when meaning matches; proposed workflow instances are distinct hypotheses, not copies of a deployed workflow.

Seed the 20 requested patterns plus a small number of software/creative/education patterns. Each needs ordered proposed steps, inputs/outputs, ownership, failure modes, specific questions, MVP boundary, maturity and evidence labels. Validate all references and reject opportunities incorrectly marked deployed. Structural graph validation does not establish real-world validity.

System Lens should distinguish existing related work, a proposed library pattern, a newly composed hypothesis and requests needing clarification. Matching uses domain + task + artifact signals and paraphrase families; it is not a semantic embedding model or general language understanding. A clean interpreter interface leaves room for a later model without letting it create product/evidence facts.

Acceptance includes the required astrology, GST/invoice, supplier, support, research and inventory cases; conventional websites/portals/creative work; a genuinely new operational request; vague and unrelated requests; explicit uncertainty; all five allocation comparisons; truthful work/capability browsing; and an exported visual opportunity workflow. Keep the existing two-path entry and deferred Google Form. No commit/push/merge/deploy.
